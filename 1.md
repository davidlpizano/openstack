# Introducción a OpenStack

## ¿Qué es OpenStack?

**OpenStack** es una plataforma de código abierto para construir y gestionar **nubes privadas y públicas** de tipo IaaS (*Infrastructure as a Service*). Permite controlar grandes conjuntos de recursos de cómputo, almacenamiento y red desde un panel web o mediante APIs, de forma similar a lo que hacen AWS, Azure o GCP, pero sobre tu propio hardware.

Nació en 2010 como un proyecto conjunto de **NASA** y **Rackspace**. Hoy lo mantiene la **OpenInfra Foundation**, integrada en la Linux Foundation, y publica una versión nueva cada seis meses. Está escrito principalmente en **Python** y se distribuye bajo licencia **Apache 2.0**.

## Conceptos clave

- **Proyecto (tenant):** unidad de aislamiento donde se agrupan los recursos de un usuario o equipo.
- **Instancia:** una máquina virtual creada a partir de una imagen.
- **Flavor:** plantilla que define vCPU, RAM y disco de una instancia.
- **Imagen:** plantilla de disco desde la que se arranca una instancia (Ubuntu, Debian, etc.).
- **Red, subred y router:** redes virtuales definidas por software para conectar instancias.
- **Floating IP:** IP pública que se asocia a una instancia para accederla desde fuera.
- **Security group:** reglas de firewall aplicadas a las instancias.

## Servicios principales

| Servicio | Nombre | Función |
|---|---|---|
| Cómputo | **Nova** | Crea y gestiona máquinas virtuales |
| Red | **Neutron** | Redes virtuales, routers, firewalls, VPN |
| Almacenamiento de bloques | **Cinder** | Volúmenes persistentes (como discos) |
| Almacenamiento de objetos | **Swift** | Almacenamiento escalable de objetos |
| Identidad | **Keystone** | Autenticación, usuarios, roles y catálogo de servicios |
| Imágenes | **Glance** | Catálogo y almacenamiento de imágenes |
| Panel web | **Horizon** | Interfaz gráfica de administración |
| Orquestación | **Heat** | Despliegue de infraestructura mediante plantillas |
| Colocación | **Placement** | Seguimiento de inventario y recursos disponibles |

Existen muchos más (Octavia para balanceo de carga, Ironic para *bare metal*, Magnum para Kubernetes, Manila para sistemas de ficheros compartidos...). Todos se comunican mediante **APIs REST** y se apoyan en una base de datos (MariaDB/MySQL) y una cola de mensajes (RabbitMQ).

## Arquitectura básica

```
                 ┌───────────────┐
   Usuario ────► │ Horizon / CLI │
                 └───────┬───────┘
                         │ API REST
                 ┌───────▼───────┐
                 │   Keystone    │  (autenticación)
                 └───────┬───────┘
        ┌────────┬───────┼────────┬─────────┐
     ┌──▼──┐  ┌──▼───┐ ┌─▼────┐ ┌─▼─────┐ ┌─▼────┐
     │Nova │  │Neutron│ │Cinder│ │Glance │ │ Swift│
     └──┬──┘  └──────┘ └──────┘ └───────┘ └──────┘
        │
   Hipervisores (KVM/QEMU) en los nodos de cómputo
```

En un despliegue típico se distinguen estos nodos:

1. **Controlador:** ejecuta APIs, base de datos, cola de mensajes y servicios de gestión.
2. **Cómputo:** ejecuta las instancias mediante un hipervisor (normalmente KVM).
3. **Red:** gestiona el tráfico virtual (a veces integrado en el controlador).
4. **Almacenamiento:** aloja volúmenes y objetos.

## Ejemplo de uso con la CLI

```bash
# Crear una red y una subred
openstack network create red-demo
openstack subnet create --network red-demo \
  --subnet-range 192.168.100.0/24 subred-demo

# Lanzar una instancia
openstack server create \
  --flavor m1.small \
  --image ubuntu-24.04 \
  --network red-demo \
  --key-name mi-clave \
  vm-demo

# Listar instancias
openstack server list
```

## Cómo probarlo

| Opción | Descripción | Recomendada para |
|---|---|---|
| **DevStack** | Script que instala un entorno completo desde el código fuente | Aprendizaje y desarrollo |
| **MicroStack** | Despliegue ligero y sencillo basado en Snap | Pruebas rápidas en un solo nodo |
| **Kolla-Ansible** | Despliegue en contenedores Docker | Entornos más realistas |
| **OpenStack-Ansible** | Despliegue de producción con Ansible | Producción |

Para empezar, DevStack en una VM Ubuntu con al menos 8 GB de RAM y 4 vCPU es suficiente.

## Ventajas e inconvenientes

**Ventajas**
- Sin dependencia de un proveedor concreto (*vendor lock-in*).
- Muy modular y extensible.
- Gran comunidad y adopción en operadores de telecomunicaciones, universidades y centros de datos.

**Inconvenientes**
- Curva de aprendizaje alta.
- Instalación y mantenimiento complejos.
- Requiere bastante hardware y conocimientos de redes y Linux.
